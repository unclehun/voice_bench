# Whisper large-v3-turbo 接入审计（0.7.1）

## 结论

已确认 0.7.0 存在会大量丢失中文的结果转换缺陷。当前 sherpa-onnx 1.13.8 在拼接 Whisper 的字节 BPE token 之前，对每个 token 清理不完整 UTF-8；一个汉字跨 token 存储时，其组成字节会被提前删除。0.7.1 增加字节安全的兼容层，继续使用现有权重、原始词表和模型 receipt，无需重新下载或传输模型。

上一版的推理、取消和清理检查主要验证流程，缺少中文 BPE 完整性回归，因此未能发现这个问题。本次增加了多语言字节边界测试，并用手机原始录音在 Mac 上做同输入、同权重的修复前后对照。

## 手机上的问题表现

2026-10-29 通过只读 USB 获取 iPhone 17 Pro 上 **0.7.0 / Build 13** 的十段结果。下表使用每段各引擎最近一条运行，全部来自 0.7.0，未剔除录音 4。参考稿包含用户提供的标题、正文及已朗读的出处。

| 引擎 | 十段总体 CER | 编辑错误数 / 参考字符数 |
|---|---:|---:|
| SenseVoice | 5.80% | 159 / 2742 |
| Apple Speech | 11.12% | 305 / 2742 |
| Qwen3-ASR | 10.87% | 298 / 2742 |
| Fun-ASR | 7.26% | 199 / 2742 |
| Whisper Turbo | 18.67% | 512 / 2742 |

Whisper 的多段中文存在明显漏字，而英文 ASCII 相对完整。这与字节 BPE 被逐片清理的机制相符；不能据此把全部差距归为模型自身的识别能力。

## 权威代码对应关系与根因

1. Whisper 的普通文本 token 保存字节片段，单片段不一定构成完整 UTF-8。例如“凯”的三个字节可以分别落在两个 token 中；两片分别转换成文本会失败，拼接字节后才能得到该字。OpenAI 的 [tiktoken 解码实现](https://github.com/openai/tiktoken/blob/main/tiktoken/core.py)先恢复完整字节流再解码文字。
2. sherpa 自己的 [Whisper ONNX Python 示例](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/scripts/whisper/test.py#L388-L393)也先拼接各 token 的 Base64 解码字节，再统一转换为 UTF-8。
3. 固定版本的原生 [Whisper 结果转换](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/csrc/offline-recognizer-whisper-impl.h#L151-L168)却逐 token 调用 `ApplyInverseTextNormalization`。该函数在没有 ITN 规则时也会先执行 [不完整 UTF-8 清理](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/csrc/offline-recognizer-impl.cc#L857-L868)，因此仅保持 ITN 配置为空无法避开丢字。
4. [whisper.cpp v1.9.5 的文本组装](https://github.com/ggml-org/whisper.cpp/blob/v1.9.5/src/whisper.cpp)同样将 token 的字节串依次追加到结果。本轮查阅了该代码，没有下载其额外模型，也没有用其引擎产生数值评测成绩。

原生探针在被漏掉的中文位置返回了空 token 字符串。使用同一 ONNX 权重的 Python 对照能恢复“困难”“项目”“愿不愿意继续”等内容，进一步定位到输出字节组装路径。

## 接入参数的审查

| 项目 | 当前实现与判断 |
|---|---|
| 音频格式 | 16kHz、单声道、Float32，与 [Whisper 官方音频入口](https://github.com/openai/whisper/blob/main/whisper/audio.py)的采样率和浮点波形约定一致。本次真实录音区间与原音频哈希已核对。 |
| 特征维数 | 128，与固定 Turbo 编码器元数据中的 `n_mels=128` 一致。 |
| 任务 | `transcribe`，配置没有请求翻译；没有将参考稿或热词传入识别。 |
| 运行框架 | 继续使用 sherpa-onnx 1.13.8 / ONNX Runtime 1.28.2，CPU 两线程；此次未更换权重或运行库。 |
| 分段与语言 | 采用约 20 秒 Silero VAD 区间、200ms 边缘保护和模型内部自动语言，能保持与 Qwen 输入流程可比；逐段独立识别会减少跨段上下文，不能视作官方整段转写的全部行为。 |
| 补齐与解码 | 动态输入、300 帧尾部补齐、greedy 解码及输出预算重试与官方完整解码流程有差别。对四个真实区间的同权重对照中，开启 token 过滤没有改变结果；改成标准 30 秒补齐也没有一致改善，所以没有把这些猜想当成本次主因。 |
| 文字转换 | 0.7.0 直接使用原生 `result.text`，继承了字节丢失缺陷；0.7.1 已增加兼容处理。 |

## 0.7.1 的修复范围

`WhisperByteTokens.swift` 为原始词表的 Base64 拼写增加一层 ASCII 传输编码。sherpa 解去外层编码后，得到的仍是有效 ASCII，能够通过其逐 token UTF-8 清理。引擎复制 `tokens_arr` 后恢复每片的原始字节，拼接为 `Data`，最后统一解码成文字。

该兼容层只改变结果传输表示：保留 token ID、原始权重、原始词表、校验清单和 receipt；推理图、VAD、语言选择和数值解码参数保持原样。临时词表写入当前录音工作目录的 `WhisperTokens-UUID.txt`，成功、失败、取消及冷启动均沿用清理机制。原始模型文件不被改写。

新运行记录 `whisper_turbo_text_decoder=base64-ascii-join-bytes-v1` 和临时词表清理状态。旧的历史转写继续保留，重新识别才会得到修复后的新结果。若模型最终输出本身含有不完整 UTF-8，解码采用 tokenizer 的替换字符语义，不根据参考稿补字。

## 真实录音的修复前后对照

只读复制手机录音 1、8 并校验源文件 SHA-256 后，在同一台 Mac 使用相同 ONNX INT8 权重、同一 Swift 引擎、同一 VAD 参数分别执行旧、新结果转换路径。两次运行的分段数和区间完全一致：录音 1 为 6 段，录音 8 为 4 段。参考稿仅用于事后计分。

| 录音 | 原实现 CER | 修复后 CER | 原实现 S / D / I | 修复后 S / D / I | 参考字符数 |
|---|---:|---:|---:|---:|---:|
| 1 | 10.50% | 2.94% | 4 / 20 / 1 | 6 / 0 / 1 | 238 |
| 8 | 23.26% | 7.64% | 14 / 52 / 1 | 16 / 2 / 4 | 288 |
| 两段加权 | 17.49% | 5.51% | — | — | 526 |

S 为替换，D 为删除，I 为插入。使用项目实际 `Evaluation.cer` 计分，仅忽略标点、空白及 ASCII 大小写，保留数字和简繁体差异。删除错误从两段合计 72 处降到 2 处，支持本次丢字根因及修复的归因。修复后仍有同音字、专名等误识。

这些是为定位问题选择的两段 **Mac 对照结果**，不能替代新版手机十段全量评测，也不能直接与上表手机总体成绩比较或据此改选最佳模型。

## 验证与剩余边界

- 34,593 项核心检查、50 项纠错检查、38 项配置文件检查通过。新增回归覆盖中文、日文、韩文、重音字母、emoji、NUL 的字节切分和重组，以及损坏词表、重复 ID 和无效 Base64 拒绝。
- 共享 Swift 引擎完成实际中文推理、真实录音前后对照、预取消、解码后取消、纯静音及派生音频和临时词表清理检查。
- 当前输出长度保护仍依赖原生结果提供的 token 数和时长预算。原生接口未直接暴露完整停止原因；被跳过的控制 token 可能不计入结果数，因此该保护不能证明所有提前停止都能被识别。
- 当前兼容层针对已锁定的库行为。未来启用 ITN / 同音替换规则或升级运行库时，应重新验证 ASCII 传输约定，并考虑在上游修正完整字节串的组装顺序。
- 本机缺 iPhoneOS SDK，本次代理未执行 iOS 编译；随后只读取得录音 4 的 0.7.1 结果且含 decoder 元数据，十段全量复测待完成。应覆盖安装新版后，保留相同模型重新识别全部十段，再比较原始 CER、英文 WER、中英混合错误率、漏段及翻译异常。
